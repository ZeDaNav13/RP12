# Selector PHC-first Identity Design

**Status:** Approved design. Implementation remains task-scoped and requires separate review before each commit.

## Goal

The Selector must identify complete equipment by its canonical physical component composition, not by its MDC codeline or by a Selector question position. An MDC remains a generated technical codeline and can be shared by configurations with different physical component PHCs.

The existing 5,940 complete-equipment PHCs are permanent historical identities. A later registry migration must preserve them exactly and allocate any newly required complete-equipment PHCs append-only.

## Canonical Physical Composition

A composition is a deterministic ordered list of physical component PHCs and quantities:

```text
[{ phc, quantity }, ...]
```

Its key is the lexicographically ordered, quantity-bearing form:

```text
PHC1:1|PHC2:2|PHC3:1
```

The rules are:

- blank physical PHCs do not participate;
- repeated PHCs aggregate their quantities;
- equal PHC and quantity sets have the same composition key regardless of selection order or Selector question position;
- any PHC or quantity difference produces a different composition key;
- selector labels, pricing, question IDs, and usage positions are not identity inputs.

## Component Data Contract

Selector question CSVs hold a first-column `phc` field. Existing option, price, code, description, compatibility, and filtering data retain their current behavior.

The current authoritative physical component values include:

- IS2 models CP10–CP60;
- VMS0706 and VCL0706 in all four distinct pump questions;
- individual chlorine probe variants, including variants that share an MDC code but have different physical PHCs;
- pH, conductivity, and porta-sondas components;
- Cabo M12.

No-selection rows, circuits, logical BDW, and Material diverso have blank component PHCs. They remain valid pricing or business-rule data where applicable but do not contribute to physical identity.

When BDW applies, it expands to two physical components:

```text
2097.SR2221U × 1
2097.SC2A2A9 × 1
```

## Complete-equipment PHC Registry

The future complete-equipment PHC registry is keyed by canonical composition, not MDC:

```text
referencia_phc,composition_key
```

Its first migration must bootstrap each existing historical composition to the existing PHC. New physical compositions append fresh sequential references and never renumber, reuse, or overwrite historical ones.

The approved design-time target with the returned client data is:

```text
11,700 raw configurations
 5,940 unique MDC codelines
 7,020 unique physical compositions
 5,940 historical PHCs preserved
 1,080 appended PHCs
534.iS200000007020 highest appended reference
```

Those figures must be independently reproduced during the registry implementation; they are not generated by this design task.

## Scope Boundaries

Task 1 introduces authoritative component PHCs and the pure composition model only. It does not alter:

- Selector runtime complete-equipment PHC lookup;
- generator identity or MDC deduplication;
- `all_reply_combinations_filtered.csv`;
- `phc_integration.csv`;
- LDM runtime or BOM behavior;
- pricing, compatibility, or MDC generation;
- release packages or ZIP generation.

The later registry/generator and Selector runtime changes must use the same pure composition model. LDM remains explicitly out of scope for this Selector phase.
